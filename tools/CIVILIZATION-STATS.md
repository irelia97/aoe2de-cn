# 民族统计

页面 `/civilizations`，导航位于玩家资料下方。支持 1v1 / 团队随机地图，以及地图、对局平均分、游戏时长组合筛选。

## 数据与统计口径

- 数据源为 AoE2 Companion Daily Matches，当前文件日期覆盖 2026-09-23 至 2026-10-24。数据及聚合库均在服务器 `/var/lib/aoe2-match-data/`，不进入项目或 Git。
- 地图为空或标记 unknown / unknow 的对局不参与任何统计。原始数据保留，聚合库重新构建。
- 胜率为获胜玩家出场数 / 玩家出场数；使用率为该民族出场数 / 全部民族出场数。
- 分数段按整场参与玩家的记录积分平均值划分；团队使用组排积分。任一参与者缺分的整场对局排除。1v1 分为 1100以下、1100~1399、1400~1699、1700~1949、1950~2149、2150~2399、2400以上；边界按 1100、1400、1700、1950、2150、2400 划分。组排分为 1100以下、1100~1399、1400~1649、1650~1849、1850以上；边界为 1100、1400、1650、1850。
- 游戏时长按 `(finished - started) * 1.7` 计算，界面显示“游戏时长”。排除不足 10 分钟的对局，按 10~20分钟、20~35分钟、35~50分钟、50分钟以上分档，分别以 10、20、35、50 分钟为左闭区间边界。
- 对位样本中，同队重复民族只记一次。团队对位表示存在该对手民族时的队伍胜率，不代表单挑胜率。镜像对位每场两侧各记一次，合计胜率 50%，样本场数去重。
- 无结果显示空状态，不额外标记小样本。

## 重建与运行

清洗后的输入位于 `processed/2026-09-23_to_2026-10-24/{rm_1v1,rm_team}/`，包含 `players.parquet` 和 `matches.parquet`。使用服务器独立虚拟环境的 DuckDB 运行：

```sh
/var/lib/aoe2-match-data/.venv/bin/python /opt/aoe2de-cn/tools/build-civilization-stats.py
```

可用 `--dataset`、`--report`、`--output` 指定新批次。生成时验证总场数、出场数、胜负数及 SQLite 完整性，通过后原子替换 `stats/civilization-stats.sqlite`。自动导入由 `aoe2-civilization-stats.timer` 管理，每周一北京时间 08:00 更新上一周周一至周日的数据。2026-10-26 跳过，首次 2026-11-02 08:00 执行，并补齐缺失的 2026-10-25。

服务通过 `AOE2_CIV_STATS_DB` 覆盖默认库路径。独立 Node worker 只读查询 SQLite，避免阻塞接收消息及网站主线程；按文件版本缓存结果 5 分钟。

- `GET /api/civilization-stats/meta`：维度与数据日期。
- `GET /api/civilization-stats`：参数 `mode`、`map`、`elo`、`duration`、`civ`；具体维度 ID 由元数据提供。
- 两个接口沿用网站来源、爬虫及限流保护；非法参数返回 400，库未就绪返回 503。

验证：`node --test tools/test-civilization-stats.mjs`；全套测试为 `node --test tools/test-*.mjs`。

## 每周自动更新

- 定时器及服务源码：`tools/systemd/aoe2-civilization-stats.{timer,service}`；入口 `tools/update-civilization-stats.py`，清洗复用 `tools/match-data-pipeline.py`，累计明细合并、验证与原始包保留由 `tools/incremental-match-data.py` 处理。
- `Persistent=true`，服务器错过计划时间时恢复后补跑；脚本的首次运行日期守卫确保 2026-10-26 不下载或更新数据。
- 从当前统计库的实际结束日期推导缺失天数，下载至上一周周日。仅下载、清洗新增日期的原始包；验证历史清洗明细后合并。按比赛 ID 替换跨批次重复比赛的整组玩家记录，再由累计明细重算统计，不依赖已删除的历史原始包。
- 上周文件未全部发布、下载损坏、清洗或统计失败时保留旧统计库；每小时重试，最多 24 次启动/两天窗口，并写入现有服务告警日志。
- 使用独占锁防止重叠任务，CPU 限额一核、内存上限 1200MB。数据一直位于 `/var/lib/aoe2-match-data/`，不进入项目目录。
- 全部校验通过后原子替换统计库，保留 `.previous.sqlite`；网页后台自动按库文件版本重载，页面日期、场数、胜率、使用率随新数据更新，无需重启网站。已打开页面在下次读取统计时获取更新。
- 保留最近 28 个已处理日期的原始包、全部处理报告和最近两份自动生成的累计清洗数据；初始清洗数据目录保留。原始包仅在确认已有完整、有效的清洗明细且统计发布成功后清理，删除前记录文件清单、大小及 SHA-256。
- 报告：`reports/weekly-latest.json`、`reports/weekly/<运行编号>/`。

只读计划检查（不下载、不写入）：

```sh
/var/lib/aoe2-match-data/.venv/bin/python /opt/aoe2de-cn/tools/update-civilization-stats.py --plan
/var/lib/aoe2-match-data/.venv/bin/python /opt/aoe2de-cn/tools/update-civilization-stats.py --plan --at 2026-11-02T08:00:00+08:00
systemctl list-timers aoe2-civilization-stats.timer
```

演练：`test-weekly-civilization-update.py` 覆盖跳过日期、跨周日期、首次缺口、缺包及构建失败不发布、完整清洗/重建/发布、重复运行不重复计数，全部使用隔离数据，无上游请求或线上数据写入。

页面的“查看民族”在条件变化后继续定位所选行，“查看对手”为下拉框；筛选场数占比的分母为该模式全部有效对局，不随筛选条件改变。

## 排名与周变化

- 民族表现按当前列排序显示 `#1`、`#2` 等排名；对位列表按所选民族胜率排序，筛选单个对手时保留其在完整对手列表中的排名。
- 周更新成功后，将上一版的元数据、民族统计和对位统计嵌入新 SQLite 的 `previous_*` 表，和新统计一次性原子发布。
- 对相同模式、地图、分数段和时长，比较本次与上次周更新后的累计胜率/使用率。地图和民族以 slug 对齐，避免重建后数字 ID 改变导致错配；分档不兼容时不作比较。
- 显示例：`53.0% +1.0%`；计算为 53.0%-52.0%=+1.0 个百分点，而非相对增长百分比。本周尚未有周更新快照，统一显示 `+0.0%`。
- 已有对比版本但相同筛选下没有该民族/对位的旧样本时显示 `—`，不虚构差值。

## 增量历史与原始包保留

`datasetPath` 指向当前累计清洗明细，`datasetChecksums` 保存四个明细文件的 SHA-256。旧版本没有该字段时，读取原始数据目录，并使用既有验证报告核对 SHA-256，同时校验匹配场数、玩家记录唯一性、胜负及队伍结构。历史原始包缺失不会阻止增量更新。

同一比赛在新增批次再次出现时，使用最新已通过清洗的完整比赛替换旧版本；不把两个版本的玩家混合，不重复累计。变更分数段、时长规则时仍可从累计清洗明细重算。

手动执行保留策略（先校验明细，再清理超过28个已处理日期的原始包，不刷新线上统计）：

```sh
/var/lib/aoe2-match-data/.venv/bin/python /opt/aoe2de-cn/tools/update-civilization-stats.py --prune-raw
```

删除审计保存在 `reports/raw-retention.jsonl`。旧的独立 `verify_processed.py` 按全部原始包仍存在设计，增量流程不再使用它。

## 累计胜率折线图

两张列表下方共用一张折线图，纵轴0～100%，横轴为每次已发布统计的数据截至日期。每个点代表该次周更新后的累计胜率，与卡片统计口径一致，不是每日或每周单独胜率。第一条为左侧所选民族的胜率；“查看对手”选择具体民族后，增加第二条对位胜率线。图表随模式、地图、积分、时长及民族筛选同步变化，悬停、点击或键盘聚焦显示完整日期、胜率及样本量。无样本或分档口径不兼容的快照留空，不连线或补零。

统计库v6保留 `trend_snapshots`、`trend_civilization`、`trend_matchup`，以民族/地图slug记录完整累计聚合快照。构建器记录当前版本，周更新发布前继承旧库全部历史快照，和当前库一起原子发布；不依赖旧原始包或仅保留一版的 `previous_*`。首次实际周更新前仅有当前基准点，不回填或虚构过去周快照。库中历史聚合会随发布次数增长，需要纳入现有数据库备份和磁盘监控。
